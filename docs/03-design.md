# 3단계 — 실험 설계와 실행

> 과제 안내 3/5 대응: T10-C21 ~ C30. 앱 버전 **1.1.0** 기준.

## 설계 표 (C21, C22)

### 바꾼 조건 (독립변수)

| 조건 | 내용 | 본 블록 |
|---|---|---|
| 신호 있음 (`cue`) | 목표 자극 500ms 전, 화면 안쪽 테두리(두께 10px, 안전 영역 안쪽)가 100ms 동안 밝아짐 | 목표 20회 + 캐치 3회 |
| 신호 없음 (`nocue`) | 같은 시점에 화면 변화 없음 | 목표 20회 + 캐치 3회 |

### 고정한 조건 (통제변수)

| 항목 | 값 | 고정한 이유 |
|---|---|---|
| 경고(가상 경고) 시점 → 목표 | 두 조건 모두 500ms | 화면에서 달라지는 것을 테두리 하나로 만들기 위해 |
| 시행 시작 → 경고 시점 | 1000–2500ms 균등분포. **같은 값 집합을 두 조건에 똑같이 배정**(짝맞춤) | 리듬을 외워 미리 누르는 것을 막고, 두 조건의 대기시간 분포를 표본 수준에서도 같게 |
| 캐치 시행 | 조건별 3회(약 13%), 원이 나오지 않음. 고정점은 반응 창이 끝날 때까지 유지 | 원이 아니라 신호에 시간 맞춰 누르는지 확인하기 위해 |
| 목표 자극 | 화면 중앙 흰 원, 지름 120px | 모든 시행 동일 |
| 응답 | 화면 아무 곳 터치·클릭, 또는 Space/Enter | 목표 위치로 손을 옮기는 시간이 반응시간에 섞이지 않도록 |
| 반응 창 | 목표(캐치는 목표가 나왔을 시점) 후 1500ms | 넘으면 놓침 / 캐치는 '잘 참음' |
| 시행 순서 | 참가자마다 무작위 (암호학적 난수) | 순서·학습·피로 효과가 한 조건에 몰리지 않도록 |
| 연습 | 조건별 목표 3회 + 캐치 1회, 분석 제외 | 과제 이해 확인, 캐치 시행 익히기 |
| 측정 시각 | 자극: 화면을 바꾼 `requestAnimationFrame` 콜백 안의 `performance.now()` / 응답: `pointerdown`·`keydown`의 `event.timeStamp`(브라우저가 이벤트를 만든 시각) | `click`은 손을 뗄 때 발생해 불필요한 지연이 섞임 |
| 실험 파라미터 | `web/src/experiment/config.js`, 앱 버전 1.1.0 | 수집 중 변경 금지 |

## 반복 횟수와 표본 수 (C23)

- 반복: 1인당 연습 8회(목표 6 + 캐치 2) + 본 블록 46회(목표 40 + 캐치 6) = **54행**
- 표본: 목표 20명 이상. 20명이면 단측 대응 t검정 기준 검정력 .80으로 dz ≈ 0.58 이상의 효과를 잡아낼 수 있다(`analysis/run_analysis.py`의 민감도 계산). 표본 수는 검정력 분석이 아니라 수집 가능 범위(지인·커뮤니티, 1주)로 정했고, 이 사실을 논문 한계에 적는다. 기간 연장은 하지 않는다.

## 측정값 (C24)

시행마다 기록하는 값(원자료 열): `session_id, trial_index, block, condition, is_catch, precue_planned_ms, cue_target_planned_ms, cue_target_actual_ms, cue_on_actual_ms, status(ok/anticipation/timeout/catch_ok/catch_fa), rt_ms, input_type(touch/mouse/pen/keyboard), time_source, hidden_during_trial, trial_started_at`

세션마다 기록하는 값: 앱 버전, 파일럿 여부, 재참여 여부, 이전 미완료 시작 여부, 조작 점검 응답(테두리를 봤는가), 연령대(선택), 브라우저 정보, 포인터 종류, 화면 크기, 화면 배율, 추정 프레임 간격, 시작·종료 시각, 서버가 기록한 배포 커밋.

이름·연락처 등 개인을 식별하는 정보는 받지 않는다.

## 원자료 (C25, C26)

- 서버 저장: 참가자 1명 = JSON 파일 1개 (Vercel Blob, `sessions/<날짜>/<session_id>-*.json`). 파일럿은 `pilot/`에 따로 저장되고 내려받지 않는다.
- 전송은 조작 점검 답 직후, 결과 화면보다 먼저 한다. 전송 전에 브라우저에 보관했다가 실패하면 다음 방문 때 다시 보낸다.
- 제출용 원자료: `data/raw/sessions/**/*.json`(원본 그대로), `data/raw/trials.csv`, `data/raw/sessions.csv`
- 건수 검증: `trials.csv`의 행 수 = 54 × 세션 수. `scripts/check_submission.py`가 자동 확인한다.

## 짧은 확인 방법 (C29)

1. **측정 도구 점검** — `cd web && npm run build && python3 e2e/system_check.py`
   브라우저 안의 로봇 참가자가 목표가 뜨면 정확히 250ms 뒤에 누르고, 캐치 시행에서는 누르지 않는다. 2026-10-30, 앱 1.1.0, 데스크톱 Chromium 결과(`docs/evidence/system-check.json`):
   - 54행(연습 8 + 본 46), 캐치 8행 모두 `catch_ok`, 일부러 넣은 조기 반응 1건이 RT 없이 기록됨
   - 대기시간 짝맞춤: 두 조건의 대기시간 집합 일치
   - 경고→목표 기록 간격 497.5–514.7ms (설계 500ms), 테두리 점등 97.9–100.8ms (설계 100ms)
   - 기록된 RT 250.1–250.5ms (로봇 250ms)
   - **이 점검이 보여 주는 것과 못 보여 주는 것**: 로봇은 같은 브라우저 시계로 DOM 변화를 감지해 합성 이벤트를 보낸다. 따라서 이 결과는 **기록 로직의 내부 일관성**이다. 실제 화면 표시 시점(보통 1프레임 뒤)과 터치스크린·키보드 하드웨어 지연은 포함되지 않는다.
2. **분석 점검** — `python3 analysis/tests/test_pipeline.py`
   유효 시행 정의의 경계 사례, 참가자 제외 규칙, 판정 규칙 반례를 단위 시험하고, 가상 데이터(효과를 심은 경우·없는 경우)로 판정이 결과에 맞춰 움직이는지, 가상 데이터가 실제 분석에서 거부되는지 확인한다. 가상 데이터는 제출물에 포함하지 않는다.
3. **실험 파라미터 단위 시험** — `cd web && npm test` (시행 수, 조건·캐치 균형, 대기시간 짝맞춤)
