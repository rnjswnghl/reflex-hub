# 3단계 — 실험 설계와 실행

> 과제 안내 3/5 대응: T10-C21 ~ C30. 앱 버전 **2.0.0** 기준.

## 실험이 놓인 자리

실험 페이지는 미니게임 허브(Reflex Hub)다. 참가자는 네 게임 가운데 원하는 것을 골라 몇 판이든 한다.
연구 데이터는 그중 **'번개 반사'** 한 게임에서만 나온다. 나머지 게임은 재미와 재방문을 위한 것이고 논문에서 분석하지 않는다.
- 기록 도전: 컬러 함정, 1→16, 딱 N초(1·3·5·10초 중 선택, [시작]→[멈춤] 한 번, 목표별 순위표)
- 전후 비교 실험실: 번개 반사 2(초록 풍경 40초)·3(심호흡 32초)·4(손가락 연타 10초). [반응 테스트 9회] → [개입] → [반응 테스트 9회]. 판마다 50% 확률로 같은 시간의 회색 화면(비교군)을 배정하고, 결과 화면에서 두 집단의 평균 변화를 나란히 보여 준다. 두 번째 테스트는 연습만으로도 빨라지므로, 비교군 없이 '빨라졌다'만 보여 주면 착시가 되기 때문이다.
'번개 반사' 한 판은 약 40초다. 같은 사람(브라우저)이 여러 판을 하면 판을 합쳐 그 사람의 값으로 쓴다(사전 등록 v3).

## 설계 표 (C21, C22)

### 바꾼 조건 (독립변수)

| 조건 | 내용 | 한 판에 |
|---|---|---|
| 신호 있음 (`cue`) | 목표 자극 500ms 전, 화면 안쪽 테두리(두께 10px, 안전 영역 안쪽)가 100ms 동안 밝아짐 | 목표 6회 + 캐치 1회 |
| 신호 없음 (`nocue`) | 같은 시점에 화면 변화 없음 | 목표 6회 + 캐치 1회 |

### 고정한 조건 (통제변수)

| 항목 | 값 | 고정한 이유 |
|---|---|---|
| 경고(가상 경고) 시점 → 목표 | 두 조건 모두 500ms | 화면에서 달라지는 것을 테두리 하나로 만들기 위해 |
| 시행 시작 → 경고 시점 | 800–2000ms 균등분포. **같은 값 집합을 두 조건에 똑같이 배정**(짝맞춤) | 리듬을 외워 미리 누르는 것을 막고, 두 조건의 대기시간 분포를 표본 수준에서도 같게 |
| 대기 표시 | 화면 가운데 회색 **'+'** | 목표(노란 원)와 모양·색이 달라 헷갈리지 않게 (v1의 회색 점은 원으로 착각하기 쉬웠음) |
| 목표 자극 | 화면 중앙 **노란 원**, 지름 120px | 모든 시행 동일 |
| 캐치 시행 | 조건별 1회(한 판의 약 14%), 원이 나오지 않음. '+'는 반응 창이 끝날 때까지 유지 | 원이 아니라 신호에 시간 맞춰 누르는지 확인하기 위해 |
| 응답 | 화면 아무 곳 터치·클릭, 또는 Space/Enter | 목표 위치로 손을 옮기는 시간이 반응시간에 섞이지 않도록 |
| 반응 창 | 목표(캐치는 목표가 나왔을 시점) 후 1500ms | 넘으면 놓침 / 캐치는 '잘 참음' |
| 시행 순서 | 판마다 무작위 (암호학적 난수) | 순서·학습·피로 효과가 한 조건에 몰리지 않도록 |
| 연습 | 브라우저의 첫 판에만, 조건별 목표 1회 + 캐치 1회, 분석 제외 | 과제 이해 확인, 캐치 시행 익히기 |
| 피드백 | 매 시행 반응시간 표시(450ms), 판 끝에 점수·순위 | 두 조건에 같게. 결과 화면에 조건 비교는 보여 주지 않음 |
| 점수 | 유효 반응시간 평균 + 실수(미리 누름·함정·놓침) 1번당 100ms | 순위 경쟁이 '미리 누르기'를 부르지 않도록 벌점 |
| 측정 시각 | 자극: 화면을 바꾼 `requestAnimationFrame` 콜백 안의 `performance.now()` / 응답: `pointerdown`·`keydown`의 `event.timeStamp`(브라우저가 이벤트를 만든 시각) | `click`은 손을 뗄 때 발생해 불필요한 지연이 섞임 |
| 실험 파라미터 | `web/src/games/reaction/config.js`, 앱 버전 2.0.0 | 수집 중 변경 금지 |

## 반복 횟수와 표본 수 (C23)

- 한 판: 본 블록 14회(목표 12 + 캐치 2), 첫 판에만 연습 4회 추가 → 첫 판 18행, 이후 판 14행
- 참가자 포함 기준: 모든 판을 합쳐 조건별 유효 목표 시행 5회 이상, 합계 10회 이상 → 실수가 적은 한 판으로도 포함 가능. 여러 판을 하면 시행이 쌓여 그 사람의 값이 더 안정된다.
- 표본: 목표 20명 이상. 20명이면 단측 대응 t검정 기준 검정력 .80으로 dz ≈ 0.58 이상의 효과를 잡아낼 수 있다(`analysis/run_analysis.py`의 민감도 계산). 표본 수는 검정력 분석이 아니라 수집 가능 범위(지인·커뮤니티, 1주)로 정했고, 이 사실을 논문 한계에 적는다. 기간 연장은 하지 않는다.

## 측정값 (C24)

시행마다 기록하는 값(원자료 열): `round_id, player_id, trial_index, block, condition, is_catch, precue_planned_ms, cue_target_planned_ms, cue_target_actual_ms, cue_on_actual_ms, status(ok/anticipation/timeout/catch_ok/catch_fa), rt_ms, input_type(touch/mouse/pen/keyboard), time_source, hidden_during_trial, trial_started_at`

판마다 기록하는 값: 판 번호, 참가자 번호(브라우저에 저장된 무작위 값), 이 브라우저에서 몇 번째 판인지, 첫 판 여부, 무작위 닉네임 번호, 앱 버전, 파일럿 여부, 조작 점검 응답(첫 판 뒤 한 번), 브라우저 정보, 포인터 종류, 화면 크기, 화면 배율, 추정 프레임 간격, 시작·종료 시각, 서버가 다시 계산한 점수, 서버가 기록한 배포 커밋.

이름·연락처 등 개인을 식별하는 정보는 받지 않는다. 닉네임은 형용사+동물 무작위 조합이다.

## 원자료 (C25, C26)

- 서버 저장: 판 1개 = JSON 파일 1개 (Vercel Blob, `sessions/<날짜>/<round_id>__s<점수>__p<참가자 앞 8자>__n<닉네임>.json`). 순위표는 파일 이름만 읽어 만든다. 파일럿은 `pilot/`에 따로 저장되고 내려받지 않는다.
- 시작 기록: 판을 시작하면 `funnel/start/<round_id>__p<참가자 앞 8자>.json` 하나(번호·시각·앱 버전만). 완료율 계산과 수집 현황판(`/stats.html`)에 쓴다. 제출용 원자료에는 `data/raw/funnel/`, `data/raw/funnel.csv`로 들어간다.
- 다른 미니게임 점수: `scores/<게임>/...` (분석하지 않음, 제출 원자료에 넣지 않음)
- 방문 통계: Vercel Web Analytics(쿠키 없음, 익명). 페이지를 연 수만 세며 분석에는 쓰지 않는다.
- 전송은 결과 화면을 띄우는 동시에 하고, 전송 전에 브라우저에 보관했다가 실패하면 다음 방문 때 다시 보낸다. 같은 판을 두 번 보내도 서버는 첫 기록만 남긴다.
- 제출용 원자료: `data/raw/sessions/**/*.json`(원본 그대로), `data/raw/trials.csv`, `data/raw/rounds.csv`, `data/raw/funnel.csv`
- 건수 검증: 판마다 `trials.csv` 행 수 = 14(첫 판 18). `scripts/check_submission.py`가 자동 확인한다.

## 짧은 확인 방법 (C29)

1. **측정 도구 점검** — `cd web && npm run build && python3 e2e/system_check.py`
   브라우저 안의 로봇 참가자가 노란 원이 뜨면 정확히 250ms 뒤에 누르고, 캐치 시행에서는 누르지 않는다. 휴대폰 크기 화면에서 '번개 반사'를 두 판 한다. 2026-10-30, 앱 2.0.0, Chromium 결과(`docs/evidence/system-check.json`) — 점검 13개 모두 통과:
   - 1판 18행(연습 4 + 본 14), 2판 14행(연습 없음), 캐치는 모두 `catch_ok`, 일부러 넣은 조기 반응 1건이 RT 없이 기록됨
   - 두 판 모두 대기시간 짝맞춤 일치, 같은 참가자 번호, 판 번호 1→2, 조작 점검은 첫 판에서만
   - 경고→목표 기록 간격·테두리 점등 시간·기록 RT가 설계 범위 안 (수치는 evidence 파일)
   - 브라우저에 저장된 최고 점수 = 서버 식으로 다시 계산한 두 판 점수의 최솟값
   - **이 점검이 보여 주는 것과 못 보여 주는 것**: 로봇은 같은 브라우저 시계로 DOM 변화를 감지해 합성 이벤트를 보낸다. 따라서 이 결과는 **기록 로직의 내부 일관성**이다. 실제 화면 표시 시점(보통 1프레임 뒤)과 터치스크린·키보드 하드웨어 지연은 포함되지 않는다.
2. **분석 점검** — `python3 analysis/tests/test_pipeline.py`
   유효 시행 정의의 경계 사례, 판·참가자 제외 규칙(여러 판 합치기 포함), 판정 규칙 반례를 단위 시험하고, 가상 데이터(효과를 심은 경우·없는 경우)로 판정이 결과에 맞춰 움직이는지, 가상 데이터가 실제 분석에서 거부되는지 확인한다. 가상 데이터는 제출물에 포함하지 않는다.
3. **실험·서버 단위 시험** — `cd web && npm test` (판 구성, 조건·캐치 균형, 대기시간 짝맞춤, 점수 식, 서버 점수 = 브라우저 점수, 순위표 파일 이름 읽기·쓰기)

## 공개 데이터 사용 여부 (C27)
